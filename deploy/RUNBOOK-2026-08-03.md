## Rollback

A release is a directory of files, so rollback is a redeploy of the previous `out/`.

| Failure | Action |
|---|---|
| The route shell is wrong | `ROUTES_ENABLED = false` in `src/lib/flags.ts`, rebuild, redeploy |
| A content defect | Revert the JSON commit, rebuild, redeploy |
| Anything else | `git checkout <prev>`, `npm run build`, `cd deploy && ./deploy.sh` |

No stored-progress migration to undo: every `Progress` field this transformation adds is
optional and defaults to empty, so a learner returning with an old save loses nothing.

**One behavioural change will read as a restriction.** The checkpoint attempt cap now
survives a refresh. It used to live in React state, and within six reloads 28 of 35
checkpoints cleared. Anyone who had been re-rolling a checkpoint with F5 can no longer do
that; that is the defect being fixed.

## Known residual risk

- **No visual regression baseline.** 110 browser tests assert structure and reachability, not pixels. A CSS regression that preserves the DOM passes everything. Highest residual risk.
- **No telemetry** (0 tracking calls), so the rollout is judged by looking. If the route split confuses learners, nothing reports it.
- **6.1 MB of assets** with no CI size budget.

## Second deploy, same day — the assessment fix

A verification round after the first deploy found that the categorize exploit fix had been
measured in the wrong coordinate space, so a second release went out.

### What changed

`displayForCategorize` guarded blind strategies against AUTHORED bucket numbers. A learner
drops a chip into a bucket POSITION, and `bucketOrder` maps position to authored bucket — so
"alternate left/right on screen" was invisible to the guard. End to end it cleared 6 of 105
checks at attempt 0 and 14 at attempt 1, while the guard and a content-side audit both
reported zero. They agreed because they shared the same error.

The guard now rejects a tray order under which EITHER reading is the key. Correcting only
screen space produced 12 new clears in authored space — the two are the same attack in
different terms, so both have to be closed at once.

Also: `bucketOrder` used `safePerm`, which bans the identity. With two buckets that leaves
exactly one permutation, so 97 of 97 two-bucket checks received the same forced `[1,0]` on
every attempt — a rename, not a shuffle. Now a real coin flip (49 of 97 draw the identity).
